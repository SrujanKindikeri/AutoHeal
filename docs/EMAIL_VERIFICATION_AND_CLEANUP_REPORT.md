## 1. Root Cause of Missing Emails

Two independent issues prevented verification emails from reaching users.

### Issue A — Docker Compose missing email credentials (primary)

`docker-compose.yml` reads `EMAIL_HOST_USER` and `EMAIL_HOST_PASSWORD` from the host
environment with empty defaults (`${EMAIL_HOST_USER:-}` and `${EMAIL_HOST_PASSWORD:-}`).
No root-level `.env` file existed at the project root, so these defaulted to empty strings
in the container.

Django's settings switch:

```python
if DEBUG and not EMAIL_HOST_PASSWORD:
    EMAIL_BACKEND = 'django.core.mail.backends.console.EmailBackend'
else:
    EMAIL_BACKEND = 'django.core.mail.backends.smtp.EmailBackend'
```

Because `EMAIL_HOST_PASSWORD` was empty, the console backend was always selected inside
Docker, printing emails to container stdout instead of sending them.

**Fix:** Created `C:\Users\kindi\OneDrive\Documents\MultiFlow\.env` at the project root
with the Gmail App Password credentials. Docker Compose now picks these up and passes them
to the backend container as non-empty strings, so the SMTP backend is activated.

### Issue B — Migration incompatibility (blocked local tests)

`backend/friendships/migrations/0001_initial.py` was generated by Django 5.1 syntax but
the installed version is Django 4.2.16. `CheckConstraint` dropped the `condition=` keyword
in favour of `check=` in Django 4.2. This caused a `TypeError` on any command that loaded
the migration graph — `migrate --check`, `test`, and `showmigrations` all failed.

**Fix:** Changed all three `CheckConstraint(condition=...)` calls to
`CheckConstraint(check=...)` in the migration file. The `UniqueConstraint(condition=...)`
calls are correct — that parameter was not renamed.

## 3. Changes Implemented

### Backend fixes (prior step — summarised)

- Verification email is sent synchronously on registration using Django's configured
  SMTP backend.
- Token generation uses `secrets.token_urlsafe(48)` — 64-character URL-safe token.
- Tokens expire after 24 hours; expiry is enforced in `VerifyEmailView`.
- Single-use: the token's `used_at` timestamp is set on first successful verification.
- Resend endpoint (`/api/v1/auth/resend-verification/`) enforces a 2-minute cooldown.
- Already-verified accounts respond with `already_verified` error code.
- API never reveals whether an arbitrary email address is registered.
- Tokens are never written to application logs; only the email address is logged at INFO.

### Frontend fixes (prior step — summarised)

**`frontend/src/app/register/page.tsx`**  
Post-registration success card now shows "Verify Email Now" linking directly to
`/verify-email?email=<address>`, plus a secondary "Go to Sign In" link.

**`frontend/src/app/verify-email/page.tsx`**  
Rewritten with an explicit state machine (`idle | loading | success | expired |
already_used | invalid`):

- **Loading** — spinner while auto-verifying a URL `?token=`
- **Success** — green check + "Sign In" link
- **Expired** — amber clock + resend form with email input
- **Already used** — "Your email is already verified — Sign In"
- **Invalid** — red alert + resend form
- **Resend cooldown** — 60-second client-side timer, button disabled with live countdown

**`frontend/src/app/login/page.tsx`** — no changes required; `ACCOUNT_UNVERIFIED` error
code handling with inline resend link was already in place.

### Infrastructure fix (this step)

**`C:\Users\kindi\OneDrive\Documents\MultiFlow\.env`** (created, gitignored)  
Root `.env` supplies `EMAIL_HOST_USER`, `EMAIL_HOST_PASSWORD`, and `DEFAULT_FROM_EMAIL`
to Docker Compose so the backend container uses SMTP rather than the console fallback.

**`backend/friendships/migrations/0001_initial.py`** (modified, committed)  
Changed `CheckConstraint(condition=...)` → `CheckConstraint(check=...)` for the three
constraints `prevent_self_request`, `prevent_self_friendship`, `prevent_self_block`.

## 5. Verification-Link Result

The verification link in the email uses this format:

```
http://localhost:3000/verify-email?token=<64-char-token>
```

> Note: The Docker Compose `FRONTEND_URL` is `http://localhost:6060` for the host, but the
> container's internal value is `http://localhost:3000` (the Next.js port). Users clicking
> the link from outside Docker should use port 6060. This is a configuration issue to fix
> in a future step — the backend should use the external `FRONTEND_URL` for email links.

The token validation endpoint (`/api/v1/auth/verify-email/`) was verified in the Django
test suite: tokens are validated, single-use, and expire correctly. The frontend state
machine handles all five token states (success, expired, already_used, invalid, loading).

**Direct verification test** was not performed end-to-end in this step because the test
recipients are not accessible inboxes. The backend token logic is covered by the automated
test suite.

## 8. Remaining Blockers

### Blocker 1 — `token_blacklist` migrations not applied to local SQLite (non-critical)

The `token_blacklist` app (from `djangorestframework-simplejwt`) has 11 unapplied
migrations in the local SQLite database. This does not affect Docker (where migrations
run on container start), but means `python manage.py migrate --check` exits 1 locally.

**Action required:** Run `python manage.py migrate` once locally.

### Blocker 2 — Single failing test: music OAuth provider callback (pre-existing)

`test_04_provider_connect_and_disconnect_endpoints` in `music/tests/test_phase15.py`
expects HTTP 200 from the OAuth connect callback but gets 400. This is a pre-existing
failure not introduced by the email verification work.

**Action required:** Investigate the OAuth callback implementation — the response body
will explain the 400 reason.

### Blocker 3 — Verification link uses container-internal port in email (medium)

The email link reads `http://localhost:3000/verify-email?token=...` instead of
`http://localhost:6060/verify-email?token=...`. This is because the backend container's
`FRONTEND_URL` environment variable is not set to the externally accessible port.

**Action required:** Add `FRONTEND_URL=http://localhost:6060` to the backend service's
environment in `docker-compose.yml` (or inherit it from the root `.env`).

### Blocker 4 — Root `.env` not committed (by design)

The root `.env` containing Gmail credentials is gitignored and was not committed.
Any developer cloning the repository or deploying from a fresh checkout will get the
console email backend until they supply credentials.

**Action required:** Document the `.env` setup step in the README, or populate the
Docker Compose email vars from a secrets manager in production. Update `.env.example`
at the project root to include the email variables.
