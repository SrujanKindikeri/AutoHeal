# MovieFlow — Backend Real-Time Core, Rooms & Personal Media Uploads
## Technical Design

**Scope:** Backend only (`backend/`, Django 5.1 + Channels 4 / Daphne). This design implements the requirements in `01-requirements.md`. No frontend changes.

**Run type:** Revision. A `design-review.json` / `03-design-review.md` exists in this run directory with verdict `CHANGES_REQUESTED` (1 HIGH, 8 MEDIUM, 7 NIT). This revision addresses every finding; the per-finding disposition is in §16. All claims about existing code below were verified against the source in `backend/`.

---

## 1. Overview

MovieFlow's real-time core is almost entirely absent from the backend today: the `playback` models have no migration and no API, `rooms` exposes only three broken invitation endpoints, there is no room-creation or join endpoint, there is no WebSocket consumer (only `ws/health/`), the ASGI layer authenticates WebSockets by session while the frontend uses JWT in localStorage, the provider package is half-deleted and unimportable, and there is no personal-media upload anywhere. This design wires all of that together against the existing models without inventing new patterns.

The design centers on four additions, each fitted to existing conventions:

1. **Additive migrations** for `playback` (one `0001_initial` creating all six existing model tables) and the missing `rooms`/`library` tables and columns — generated by `makemigrations` so they match the models exactly, then verified additive.
2. **A JWT WebSocket auth middleware** that reads `?token=<jwt>` and populates `scope['user']`, plus a single room/playback consumer at `ws/rooms/<room_id>/` that owns server-authoritative state in `RoomPlaybackState` and broadcasts to a `room_<id>` group.
3. **A complete Rooms REST API** (`rooms/serializers.py`, `rooms/views.py`, `rooms/urls.py`) with custom DRF permission classes, fixing the invitation field mismatch and adding room + invitation creation, list/detail, join/leave/end/kick.
4. **Personal media uploads** as additive `library` models (`UserMovie`, `UserTrack`) with content-sniff validation (no new dependency), uuid-safe filenames under `MEDIA_ROOT`, and an authenticated, Range-aware streaming view that checks ownership or room membership — never exposed under the public `MEDIA_URL`. A fresh, minimal provider registry (`playback/providers/base.py` + `registry.py`) backs a `/api/v1/playback/` capability surface. A `cleanup_expired_rooms` management command closes stale rooms and removes stale invitations.

The approach is deliberately conservative: reuse the existing `RoomPlaybackState.compute_current_position` server-authoritative model, reuse existing `Room`/`RoomParticipant`/`RoomInvitation`/`RoomSettings` semantics, reuse the existing `music.Playlist` model (via a cross-app relation) rather than duplicating playlist logic, and reuse the existing per-app `APIView` + `IsAuthenticated` pattern used by `library` and `music`. The only model edits are additive (`Room.password_hash`; the already-defined-but-unmigrated `RoomParticipant`/`RoomSettings` fields get their columns).

## 4. Data model & migrations (Requirement A)

All migrations are additive (create new tables, add new columns with defaults, or choice-only `AlterField`). None drops a table or column.

### 4.1 `playback/migrations/0001_initial.py` (A1, F4 — reconciled)

`makemigrations playback` generates one migration creating all six existing models: `PlaybackProvider` (CharField slug PK), `UserProviderConnection`, `ContentProviderAvailability`, `PlaybackSession`, `RoomPlaybackState`, `PlaybackEvent`. Dependencies: `('rooms', '0001_initial')` (FKs to `rooms.Room`) + `swappable_dependency(AUTH_USER_MODEL)`. Creation order inside the migration is provider → connection → availability → session → state → event so all FKs resolve.

**Apparent A1 vs F4 tension, resolved:** A1 asks for an `0001_initial` for *all* playback models; F4 asks for a migration "only for the provider/session tables you actually use." The clean resolution is a **single** `0001_initial` that creates all six tables in one additive migration. This satisfies A1 (all models migrated, `makemigrations --check` clean) and is the minimal *number* of migrations (F4's "minimal and additive"). Only `RoomPlaybackState` and `PlaybackEvent` are written by the consumer this run; `PlaybackProvider`/`PlaybackSession`/`UserProviderConnection`/`ContentProviderAvailability` tables exist for consistency and future provider persistence, but this run's provider REST surface reads the **in-memory registry** (`playback/providers/registry.py`), not the `PlaybackProvider` table. No model field needs changing — all fields are standard and migrate cleanly. Index names are explicitly named in the models (e.g. `playback_pl_provide_bced8a_idx`), avoiding SQLite index-name clashes.

### 4.2 `rooms/migrations/0002_invitations_settings_personal.py` (A2)

`makemigrations rooms` detects (a) the unmigrated models, (b) the columns already-defined in the model but missing from `0001_initial`, and (c) the choice expansion on `RoomEvent.event_type`. The generated `0002` is additive and contains:

- **CreateModel:** `RoomInvitation`, `RoomMessage`, `RoomMessageReaction`, `RoomMessageReport`, `RoomMute`, `VoiceSession`, `VoiceParticipant`, `RoomRolePermission`, `RoomSettingsRevision`.
- **AddField on `Room`:** `password_hash` (`models.CharField(max_length=255, blank=True, default='')`) — the optional private-room password (decision 3 / assumption: additive column, hash via `make_password`, never stored in plaintext; `max_length=255` bounds the `make_password` output which is ~78–100+ chars). *(Finding 14)*
- **AddField on `RoomParticipant`:** `readiness_state`, `readiness_updated_at`, `connection_status`, `last_seen_at`, `is_mic_muted`, `is_camera_off`, `device_check_completed` — all already in the model with defaults/`null=True`, so AddField is safe.
- **AddField on `RoomSettings`:** `chat_permission_mode`, `voice_permission_mode`, `video_permission_mode`, `room_reminders_enabled`, `participant_join_alerts`, `room_event_alerts`, `allow_cohosts`, `invite_policy` — all already in the model with defaults, safe AddField. (`RoomSettings.playback_permission_mode` default `host_only` is already in 0001, so §7.3's "default = host-only" holds.)
- **AlterField on `RoomEvent.event_type`:** `0001_initial` defines 12 event choices; the current model defines ~24 (adds `participant_promoted`, `participant_demoted`, `permissions_updated`, `host_transferred`, `readiness_updated`, `connection_established`, `connection_lost`, `device_state_updated`, `invitation_sent/accepted/rejected/revoked`). `makemigrations` emits an `AlterField` (choice expansion only). This is **data-safe**: the column is a plain `CharField`, choices are validation-only, and existing rows are untouched. *(Finding 10)*

Voice/mute/report/role-permission/settings-revision tables are created because they are defined in `models.py` (the requirements explicitly accept this). They are inert this run — the consumer uses only `Room`, `RoomParticipant`, `RoomSettings`, `RoomInvitation`, `RoomEvent` — but creating them avoids a permanent `makemigrations --check` failure. `RoomMessage` is created and used only for the consumer's optional system-event persistence (participant join/leave system notices); a full chat REST surface stays out of scope.

### 4.4 Content-reference convention (resolves the "personal content_type" assumption)

To avoid changing `Room.CONTENT_TYPE_CHOICES` or `Room.clean()` (which would force a model choice edit), personal uploads reuse existing content types with a `personal` provider slug:

- A personal movie room: `content_type='movie'`, `content_id=str(UserMovie.id)`, `playback_provider='personal'`.
- A personal music room: `content_type='track'`, `content_id=str(UserTrack.id)`, `playback_provider='personal'`.

`Room.clean()` already accepts `movie` for movie rooms and `track` for music rooms, so **no model change is needed** for content compatibility. The consumer resolves `playback_provider == 'personal'` by loading `UserMovie` (movie rooms) or `UserTrack` (music rooms) by `content_id`; external content (`tmdb`, `musicbrainz`, `youtube-embed`) is resolved by provider slug. This is the single, consistent content-reference shape.

**Scope restriction for the `personal` provider this run (Finding 7):** `Room.clean()` allows `content_type='playlist'`/`'album'` for music rooms, and the design's own `UserTrackPlaylistItem` makes personal playlist membership possible — but the consumer's resolution rule only loads a single `UserMovie`/`UserTrack` by `content_id`. To avoid a creatable-but-unresolvable room, `RoomCreateSerializer` **rejects** `playback_provider='personal'` when `content_type` is `album`, `playlist`, or `tv_show`, returning a `400` with `INVALID_PERSONAL_CONTENT_TYPE`. (Personal `movie` and `track` single-item rooms are the only supported personal room shapes this run.) Resolving a personal playlist/album room to its `UserTrackPlaylistItem` tracks is **backlogged** (§15). External `playlist`/`album`/`tv_show` rooms (via `musicbrainz`/`tmdb`/`youtube-embed`) remain supported as before because their resolution path does not go through `UserMovie`/`UserTrack`.

## 5. WebSocket auth + routing (Requirement B)

### 5.1 `accounts/middleware.py` — `JWTQueryAuthMiddleware`

A channels ASGI middleware (inner-wrapping pattern) that parses the JWT from the query string and populates `scope`. It uses simplejwt's own config so it tracks whatever `USER_ID_FIELD`/`USER_ID_CLAIM` the project uses (defaults `id`/`user_id`):

```python
from urllib.parse import parse_qs
from channels.db import database_sync_to_async
from django.contrib.auth import get_user_model
from django.contrib.auth.models import AnonymousUser
from rest_framework_simplejwt.tokens import AccessToken
from rest_framework_simplejwt.settings import api_settings
from rest_framework_simplejwt.exceptions import TokenError

class JWTQueryAuthMiddleware:
    def __init__(self, inner): self.inner = inner
    async def __call__(self, scope, receive, send):
        scope = dict(scope)
        query = parse_qs(scope.get('query_string', b'').decode())
        token = query.get('token', [None])[0]
        scope['user'] = AnonymousUser()
        scope['ws_auth_error'] = None
        if token:
            try:
                access = AccessToken(token)                       # validates signature/expiry
                user_id_claim = api_settings.USER_ID_CLAIM         # default 'user_id'
                user_id = access[user_id_claim]
                User = get_user_model()
                user = await database_sync_to_async(User.objects.get)(pk=user_id)
                if user.is_active:
                    scope['user'] = user
                else:
                    scope['ws_auth_error'] = 'inactive'
            except (TokenError, KeyError, get_user_model().DoesNotExist):
                scope['ws_auth_error'] = 'invalid_token'
        return await self.inner(scope, receive, send)
```

Validation rules:
- **No `token` param:** `scope['user'] = AnonymousUser()`, `ws_auth_error = None`. The consumer decides whether a user is required.
- **Token present but invalid/expired** (`TokenError`): user stays anonymous, `ws_auth_error = 'invalid_token'`. The room consumer treats this as unauthenticated and closes.
- **Valid token, active user:** `scope['user']` set to the real `User`.

### 6.2 `rooms/permissions.py`

```python
class IsHost(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):  # obj is Room
        return RoomParticipant.objects.filter(
            room=obj, user=request.user, role=RoomParticipant.ROLE_HOST,
            status=RoomParticipant.STATUS_JOINED).exists()

class IsRoomParticipant(permissions.BasePermission):
    def has_object_permission(self, request, view, obj):
        return RoomParticipant.objects.filter(
            room=obj, user=request.user,
            status__in=[RoomParticipant.STATUS_JOINED, RoomParticipant.STATUS_APPROVED]).exists()
```

Views load the `Room` via `get_object_or_404` and call `self.check_object_permissions(request, room)` so `IsHost`/`IsRoomParticipant` have the room as `obj`.

### 6.3 Serializers (`rooms/serializers.py`)

respecting `max_participants` (409 `ROOM_FULL` if at capacity and the user wasn't already a participant), marks invitation `accepted`, sets `invitee=request.user`. Returns the room detail (so the frontend can connect to the WS). This removes the `AttributeError` 500s and makes the accept flow complete (Acceptance 4b). `get_or_create` is **not** used anywhere a returning user is expected — `update_or_create` (fetch-and-update) is used in REST accept, REST join, and WS connect so an existing `(room, user)` row with `status='left'` is flipped back to `joined`. *(Finding 13)*

### 6.5 Join endpoint (C4, private-room enforcement)

`POST /rooms/<id>/join/` body `{token?, password?}`:
- **Public room:** `update_or_create` a `joined` participant (respect capacity; 409 if full and not already a participant). Password ignored.
- **Private room:** require a valid, non-expired, **pending** `RoomInvitation` whose `room == this room` and whose invitee/email matches the user (or an open invitation). The token may come from the body or be implied by an existing pending invitation for this user. If valid → mark invitation accepted, `update_or_create` the `joined` participant. If the room has `password_hash` set, also require a matching `password` (`check_password`) — a valid token **or** a valid password satisfies private access. **No valid invitation/password → 403 `PRIVATE_ROOM_ACCESS_REQUIRED`** (Acceptance 4a: a non-member cannot join by room ID alone).
- **`require_approval=True` requested-join flow:** backlogged (Out of Scope this run). Host approval is operationalized through the invitation flow: the host creates an invitation → the invitee joins via token. This meets the "host approval/invite" alternative without a separate approval-request subsystem.

Return the room detail (members + playback state + content).

### 6.6 Leave / End / Kick (C5, D6)

- **Leave:** `update` the participant `status=left`, `left_at=now`, `connection_status=disconnected`. If the leaver is the host: pick the oldest other `joined` participant, promote to `host` (broadcast `host_changed` via a `RoomEvent` + the consumer's group on next connect), else set room `status=ended`, `end_time=now`. The WS consumer mirrors this on disconnect.
- **End (host):** set room `status=ended`, `end_time=now`; mark all joined participants `left`. The consumer broadcasts `room_ended`.
- **Kick (host):** target participant `status=removed`, `left_at=now`. Host cannot kick themselves. The consumer removes them from the group.

### 6.7 Invitation creation (C6)

`POST /rooms/<id>/invitations/` (`IsHost`): per §6.3 — create/reuse a `RoomInvitation` with a unique token, `expires_at` (default 7 days), `inviter=request.user`, `invitee`/`email` from body. Returns `{id, token, invite_url: f"{FRONTEND_URL}/invitations/{token}", expires_at, status}` (`status` is `pending` for a new invite or `already_pending` when reusing an existing one). Email delivery is out of scope (Out of Scope); the token/link is returned for the host to share.

## 7. Playback sync WebSocket consumer (Requirement D)

`rooms/consumers.py` — `RoomPlaybackConsumer(AsyncWebsocketConsumer)`. All ORM calls are wrapped in `database_sync_to_async`.

### 7.1 Connect

1. Read `scope['user']`. If `not user.is_authenticated` or `scope.get('ws_auth_error')` → `await self.close(code=4401)` (B2).
2. Parse `room_id` from URL kwargs; `Room = await get_room_or_none(room_id)`. If missing → `close(4404)` (D7).
3. **Private gate (D1, decision 4):** if `room.visibility == private` and the user is not an existing `joined`/`approved` participant and has no valid pending invitation for this room → `close(4403)`. **Invitation match rule (Finding 12):** a pending invitation matches the connecting user if `inv.invitee_id == user.id` **or** (`inv.invitee is None` and `inv.email == user.email`), and `not inv.is_expired`. Email-only invitations (`invitee is None`, `email == user.email`) therefore connect directly via WS — the consumer treats a matching pending email-invite as authorization to connect and auto-joins them (step 5). (Email-invite users are not *required* to REST-accept first; the WS connect path is an equally valid entry point.)
4. **Capacity gate (Finding 6):** count `RoomParticipant` with `status='joined'` for the room. If `count >= room.max_participants` **and** the user is not already a `joined` participant → `await self.close(code=4409)` (`ROOM_FULL` — documented in §7.6). This makes the WS join path consistent with the REST 409 `ROOM_FULL` gate.
5. `update_or_create` the `RoomParticipant` (existing row → flipped to `joined`, `joined_at=now`, `left_at=None`, `connection_status='connected'`, `last_seen_at=now`; new row → role `participant`, status `joined`). Add to group `room_<id>`. `await self.accept()`. *(Finding 13: update_or_create, not get_or_create.)*
6. Send full current authoritative state: `{type: 'playback_state', state: RoomPlaybackState.to_dict() or defaults, participants: [...], content: <resolved>}` (D1, D5).

### 7.2 Message protocol

Client → Server (JSON):
```json
{"action": "play" | "pause" | "seek" | "change_content" | "sync_position" | "request_state",
 "position": <float seconds>,          // seek/sync_position
 "content": {<content reference>}}      // change_content
```
Server → Client:
```json
{"type": "playback_state", "state": {...}}     // authoritative snapshot
{"type": "presence", "participants": [...]}    // participant list
{"type": "participant_joined", "participant": {...}}
{"type": "participant_left", "participant": {...}, "new_host": {...}|null}
{"type": "host_changed", "new_host": {...}}
{"type": "room_ended"}
{"type": "error", "code": "...", "message": "..."}
```
Volume is never accepted or broadcast (D3).

### 7.3 Host-only control & state persistence (D2)

A helper `_is_controller(user, room)` returns `True` for the `host`, or for a `co_host` **only when** `room.settings.playback_permission_mode` is `everyone` or `host_and_cohosts` (default `host_only`, so default = host-only — Acceptance 4c). Non-controllers issuing `play`/`pause`/`seek`/`change_content` get `{type:'error', code:'FORBIDDEN_CONTROL'}` and no state change (D7).

Each control command, for the `room`'s `RoomPlaybackState` (get_or_create):
- **`play`:** capture `position = compute_current_position()`, set `is_playing=True`, `status=playing`, `position_seconds=position`, `last_updated_at=now`, `updated_by=user`, `version+=1`, `sequence_number+=1`. Persist a `PlaybackEvent(event_type=EVENT_PLAY, ...)` (new_position=position).
- **`pause`:** `position = compute_current_position()`, `is_playing=False`, `status=paused`, `position_seconds=position`, `last_updated_at=now`, `version+=1`, `sequence_number+=1`. Persist `PlaybackEvent(EVENT_PAUSE)`.
- **`seek`** (requires `position` ≥ 0): `position_seconds=position`, `last_updated_at=now` (keep `is_playing`), `version+=1`, `sequence_number+=1`. Persist `PlaybackEvent(EVENT_SEEK, new_position=position)`.
- **`change_content`** (requires `content`): validate the new reference — a `personal` reference requires the `UserMovie`/`UserTrack` to be **owned by the host** (external references are accepted as-is). Set `current_content=content`, `position_seconds=0`, `is_playing=False`, `status=idle`, `last_updated_at=now`, `version+=1`, `sequence_number+=1`. Then broadcast `{type:'playback_state', state: state.to_dict()}` to `room_<id>` (D2, D3). On reconnect any client resyncs from the authoritative `to_dict()` (D5). *(Finding 16: ownership rule stated, parenthetical removed.)*

**`change_content` audit record (Finding 9):** the model's `PlaybackEvent` event types are `PLAY`/`PAUSE`/`SEEK`/`BUFFERING`/`RESUMED`/`ENDED`/`ERROR`/`HOST_CHANGED`/`PARTICIPANT_JOINED`/`PARTICIPANT_LEFT` — there is no `CHANGE_CONTENT`, and adding one would require an `AlterField` the design's "no model edits" stance avoids. `change_content` is therefore logged as **`PlaybackEvent.EVENT_SEEK` with `new_position=0` and `metadata={'content_changed': True, 'content': {…}, 'previous_content': {…}}`**. This reuses an existing event type, records the transition immutably, and signals the content change via `metadata` (which `PlaybackEvent.to_dict()` already exposes). No model change.

### 7.4 `sync_position` (D5 drift tolerance)

`sync_position` from the **host** updates `position_seconds` to the supplied value (keeps `is_playing`) and rebroadcasts — this is the drift-reconciliation path. From a non-host it is accepted but **ignored** (no state change, no error) so clients can report their local position without it being a hidden control path.

### 7.5 Participant & host lifecycle (D4, D6)

On a participant's connect: broadcast `participant_joined` to the group. On `disconnect`: mark the participant `connection_status=disconnected`, `last_seen_at=now`; if they were `joined`, set `status=left`, `left_at=now`, broadcast `participant_left`. **Host disconnect:** promote the oldest other `joined` participant to `host` (broadcast `host_changed`), else set room `status=ended` and broadcast `room_ended`. Remove from the group. This mirrors the REST leave/end logic so both paths stay consistent.

### 7.6 Error handling (Consumer, D7)

| Condition | Behavior |
|---|---|
| Bad JSON | `{type:'error', code:'BAD_MESSAGE'}`; connection stays open |
| Unknown action | `{type:'error', code:'UNKNOWN_ACTION'}` |
| Unknown room (connect) | `close(4404)` |
| Unauthenticated/invalid token (connect) | `close(4401)` |
| Private non-member (connect) | `close(4403)` |
| Room at capacity and user not joined (connect) | `close(4409)` *(Finding 6)* |
| Non-controller control | `{type:'error', code:'FORBIDDEN_CONTROL'}` (no state change) |
| `seek`/`change_content` missing required field | `{type:'error', code:'VALIDATION_ERROR', message:...}` |
| `change_content` personal item not owned by host | `{type:'error', code:'INVALID_CONTENT_REFERENCE'}` |
| Unexpected exception in handler | `{type:'error', code:'INTERNAL'}`, logged at `rooms.consumers` ERROR level; consumer stays open |

The consumer never crashes the connection on a message error (D7). All DB writes are transactional per command; a failed write logs and returns an error event without broadcasting partial state.

### 8.1 Storage & safe filenames (E4)

`library/storage.py` provides `upload_to` callables. The user-supplied filename is **never** used for the path; the stored extension is taken from the **sniffed** family, passed from the view through the instance (Finding 5 — `upload_to` itself has no access to the sniffed family, so the view sets `instance._stored_ext` before save):

```python

    return f'user_movies/{uuid4().hex}{ext}'
def user_movie_poster_path(instance, filename):
    return f'user_movie_posters/{uuid4().hex}{Path(filename).suffix.lower()[:10] or ".jpg"}'
def user_track_file_path(instance, filename): ...        # user_tracks/
def user_track_cover_path(instance, filename): ...       # user_track_covers/
```

The user's original filename is stored separately in `original_filename` (for display only). Because the path is fully server-generated from a UUID, path traversal via a crafted filename is impossible (the `filename` argument is never used for the path). `FileField`/`ImageField` storage is the default `FileSystemStorage` rooted at `MEDIA_ROOT`. *(Finding 5: extension now comes from the sniffed family consistently; §8.2 wording matches.)*

### 8.2 Content validation (E2)

`library/content_validation.py` — a magic-byte sniffer (no `python-magic`). It reads the first ~512 bytes of the uploaded file and identifies the family by signature:
- **Video:** MP4 (`....ftyp`), WebM (`1A 45 DF A3`), MKV (`1A 45 DF A3`), MOV (`....moov`/`ftypqt`), AVI (`RIFF....AVI`).
- **Audio:** MP3 (`ID3` or `FF FB`/`FF F3`/`FF F2`), M4A/AAC (`....ftypM4A`), OGG (`OggS`), FLAC (`fLaC`), WAV (`RIFF....WAVE`).

The view: (1) checks `file.size` against the size limit **before** reading bytes; (2) `file.seek(0)`; reads the first 512 bytes; `sniff()` → family + recommended extension; **(3) `file.seek(0)` again** so the file pointer is back at the start before the serializer/storage saves it (Finding 15 — without this reset the stored media would be offset/truncated); (4) compares the sniffed family to the request's declared `Content-Type` (from the multipart file part) and to the field's expected family (movie upload must sniff as video; track upload must sniff as audio). **A mismatch (e.g. an `.mp4`-named file whose bytes are PNG) → 400 `CONTENT_TYPE_MISMATCH`** (Acceptance 4d). The sniffed MIME is stored in `content_type`; the stored extension is taken from the sniffed family (set as `instance._stored_ext`), not the upload name.

### 8.3 Size limits (E2, N5)

### 8.5 Authenticated streaming (E3, N3)

`GET .../stream/` — `_can_stream(user, item)`:
- `item.owner == user` → allow.
- Else: find rooms that reference this item. A room references a personal upload if `room.playback_provider == 'personal'` and (`room.content_id == str(item.id)` **or** the room's `RoomPlaybackState.current_content` (parsed in Python) `content_id == str(item.id)`). For each such room, allow if `RoomParticipant(room=room, user=user, status='joined')` exists.
- Else → **403** (Acceptance 4e: authenticated non-owner non-member rejected). Not-found items return 404 (owned-check first), so existence isn't leaked to non-owners.

**Range handling (Finding 4):** `FileResponse` + `seek` cannot deliver a partial chunk (it streams `start..EOF` with the wrong `Content-Length`). Streaming uses an explicit chunk-limited generator on a `StreamingHttpResponse`:

```python
def _range_reader(fh, start, end, chunk=64 * 1024):
    fh.seek(start)
    remaining = end - start + 1
    while remaining > 0:
        data = fh.read(min(chunk, remaining))
        if not data:
            break
        remaining -= len(data)
        yield data

# in the view:
if range_header_present_and_parseable:
    resp = StreamingHttpResponse(_range_reader(f, start, end), status=206, content_type=item.content_type)
    resp['Content-Length'] = str(end - start + 1)
    resp['Content-Range'] = f'bytes {start}-{end}/{size}'
    resp['Accept-Ranges'] = 'bytes'
else:
    f.seek(0)
    resp = StreamingHttpResponse(_range_reader(f, 0, size - 1), status=200, content_type=item.content_type)
    resp['Content-Length'] = str(size)
    resp['Accept-Ranges'] = 'bytes'
```

- If `Range` present and parseable (`bytes=start-end`, clamped to `[0, size-1]`): stream only `start..end`, set `Content-Range` + `Content-Length` + `Accept-Ranges`, `status=206`.
- Else (absent/unparseable): full-stream `status=200` (degrade gracefully, per §8.7). `Content-Type` from the sniffed `content_type`.
- Private files are served only through this view — they are **never** added to the public `MEDIA_URL` static route (which only runs in `DEBUG` for avatars anyway). Even in DEBUG, user media under `user_movies/`/`user_tracks/` is only reachable via the authenticated stream view.

### 8.6 Delete (E4)

```python
def capabilities(): return [p.get_capabilities() for p in all_providers()]
```

```python
            default=int(os.getenv('ROOM_INACTIVITY_TIMEOUT_MINUTES', '60')))
        parser.add_argument('--invitation-retention-minutes', type=int,
            default=int(os.getenv('ROOM_INVITATION_RETENTION_MINUTES', '0')))  # 0 = delete immediately once terminal
        parser.add_argument('--dry-run', action='store_true')
```

Logic (all counts reported; `--dry-run` reports without writing):
1. **Invitations — expire:** `RoomInvitation.objects.filter(status='pending', expires_at__lt=now()).update(status='expired')` (bulk; same semantics as `check_and_mark_expired`). Count.
2. **Invitations — remove:** `RoomInvitation.objects.filter(status__in=('expired','rejected','revoked'), expires_at__lt=now()-timedelta(minutes=RETENTION_MIN)).delete()` — deletes the terminal rows. With the default retention `0`, a pending invitation that just crossed `expires_at` becomes `expired` in step 1 and is deleted in step 2 on the same run, so a test asserting "an expired invitation is gone" passes. Count.
3. **Inactive rooms:** rooms with `status in ('live','waiting')` where `end_time__lt=now()` **or** no `RoomParticipant` with `connection_status='connected'` (or `last_seen_at` older than the threshold) → set `status='ended'`, `end_time=now()`, mark `joined` participants `left`. Count.
4. Write a `RoomEvent(room_ended)` for each closed room. `ROOM_INACTIVITY_TIMEOUT_MINUTES` and `ROOM_INVITATION_RETENTION_MINUTES` are read from env/settings (N5). **No Celery** — documented for cron in the command help. *(Finding 2.)*

## 11. Edge cases & invariants

| Invariant | Owner layer | Why |
|---|---|---|
| Private room never joinable by ID alone | REST join view + consumer connect (decision 4) | Two enforcement points: HTTP join and WS connect both require token/password/membership |
| WS join respects capacity | REST join (409) + consumer connect (`close 4409`) | Both paths gated; WS connect never silently exceeds `max_participants` *(Finding 6)* |
| Volume never synced | Consumer (only `play`/`pause`/`seek`/`change_content`/`sync_position` accepted) | Explicit allow-list of actions; `volume` field ignored |
| Server-authoritative position | `RoomPlaybackState` (consumer writes; `compute_current_position` recomputes) | Single source of truth; clients only reconcile via host `sync_position` |
| `personal` provider restricted to single items | `RoomCreateSerializer` (400 on `album`/`playlist`/`tv_show`) | Avoids creatable-but-unresolvable rooms *(Finding 7)* |
| Duplicate pending invitation cannot 500 | `RoomInvitationCreateSerializer` (reuse / `IntegrityError` catch) | `unique_pending_room_*` constraints satisfied without 500 *(Finding 8)* |
| Re-join re-activates a `left` participant | `update_or_create` in REST accept/join + WS connect | `unique_room_user_participant` means the row already exists *(Finding 13)* |
| Personal files never public | Stream view (authz check) + files stored under `user_*` not served by `MEDIA_URL` static route | Defense in depth: storage path + serving view |
| No path traversal | UUID-only storage paths (`library/storage.py`) | User filename never used in path |
| Host-only control | `IsHost` (REST) + `_is_controller` (consumer) | Default `RoomSettings.playback_permission_mode='host_only'` → host-only by default |
| No data loss on migrate | Additive migrations only (CreateModel + AddField-with-default + choice-only AlterField) | Existing rows untouched *(Finding 10)* |
| Existing features keep working | No changes to accounts/friendships/notifications/entertainment/music/library working code; only additive library models + new rooms/playback files + distinct `uploads/` prefix (no `library/movies/` collision) | Isolation of new code *(Finding 1)* |

Edge cases handled: reconnect resync (always send state on connect), host disconnect (transfer or end), partial-broadcast safety (broadcast only after successful DB write), bad JSON/unknown action (error event, no crash), range unparseable (degrade to full stream), file pointer reset after sniff (no truncation), file missing on delete (log + succeed), capacity-full join (409 REST / 4409 WS), invitation expired/revoked (410), duplicate pending invitation (reuse, never 500).

## 15. Backlog / explicit out-of-scope (for transparency)

- **Requested-join approval flow** (`require_approval`): not built this run; host approval is realized via the invitation flow. Backlogged because the only acceptance criterion touching private access (4a) is satisfied by the token gate.
- **Personal playlist/album rooms:** the `personal` provider is restricted to single `movie`/`track` items this run (`RoomCreateSerializer` rejects `album`/`playlist`/`tv_show`). Resolving a personal playlist room to its `UserTrackPlaylistItem` tracks in the consumer is backlogged *(Finding 7)*.
- **Playlist auto-advance in the consumer:** the consumer handles a single `current_content`; host `change_content` moves to the next track manually. Auto-advancing through a playlist is backlogged.
- **Music-app serializer integration of `UserTrackPlaylistItem`:** the relation exists and is managed via library endpoints; surfacing uploaded tracks inside the `music` playlist detail serializer is backlogged (frontend can merge).
- **`PlaybackProvider` table population / persisted provider connections:** tables exist (additive) but the REST surface reads the in-memory registry; persisting connections is backlogged.
- Email delivery for invitations (Out of Scope), administration app (Out of Scope), Celery/Postgres (Out of Scope), restoring deleted scraping code (explicitly forbidden), voice/video media transport (out of scope — consumer does playback sync only).
